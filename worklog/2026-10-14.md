## 20:10 深度分析：击中目标与成败机理（产出报告）
- 产出：`GhostLock_击中目标与成败分析报告.md`（工作区根目录）。
- **击中目标 = `ashmem_miscs->fops`**（内核镜像 .data，ashmem 驱动 miscdevice +0x10 的 file_operations 指针）。rb_erase 受控 8 字节写把它换成伪造 fops 表 → ashmem fd 的 lseek/pread 走攻击者函数 → pipe_buffer physrw → 遍历 init_task 改 cred=init_cred → insmod kernelsu.ko。
- **成败分界线不在竞态**：cp.log 101 次写尝试，write_window=1 占 93 次（92%），p0 写全部"执行"，但 **`replaced=1` 出现 0 次** 而 exploit 成功过 3 次 ⇒ **lseek 验证探针在本机是坏的**（检测不到成功写入）。kit 的 miss 判定基于坏探针。
- 真正的成败信号是 `pipe physrw read_ok=1`（成功）/ `done=0 read_ok=0`（失败）。
- 疑点：官方提取器与 kit 的 `kernel_phys_offset` 不一致（0x816E0000 vs 0x80000000），"窗口开了但 8 字节写偏"可能与此常数在某些 boot 漂移有关。
- 失败样本日志已存 `.workbuddy/logstudy/`；成功样本日志会被下次 boot 覆盖，**下次命中时循环停住，要立刻拉 dc_ksu.log/cp.log/cfi_state.log/walk_state 做黄金 diff**。
- 资料修复版本：6.1 分支 ≥6.1.175（本机 6.1.157 在窗口内）；触发点 `remove_waiter()` 代理锁回滚用 current 替代 waiter->task（CVE-2026-43499），补丁链含 CVE-2026-53163。

## 21:22 重大发现：内存碎片化 = 命中率的隐藏变量（root 实测）
- root 下测 /proc/buddyinfo（Normal 区）：**开火时（uptime~95s）order-3 大页仅 1 个、order-4+ 为 0**（严重碎片化）；`sync; echo 3 > drop_caches; echo 1 > compact_memory` 后 **order-3=3524、order-5=1543、order-10=47** —— 差 3000 多倍。
- 机理：exploit 的页准备/喷页在碎堆里落点不稳 → 8 字节写偏 → miss。碎片化就是"窗口开了但写偏"的合理解释。
- **死结确认**：drop_caches/compact_memory 都需要 root，root 又来自命中，且重启即失 → 无法在"决定性那一发"之前施加。
- **实用推论**：①**命中后别重启**——late-load root 持续到重启为止，不重启就一直是 root；②提权脚本已加强开火前清后台（am kill-all 等），尽量压低碎片化速率；③理论上的"调优后多连发"实验可做（当前调优 boot 上补发）但有 panic 丢 root 风险，待用户决定。
