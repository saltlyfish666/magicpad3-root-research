## 0. 一句话概述

**荣耀 MagicPad 3（CGL-W00，MagicOS 10.0.0.170）的 root 通过 GhostLock（CVE-2026-43499，futex PI 栈 UAF）赞助版工具实现**。root 非持久（重启即失），需在每次重启后重跑提权。整套流程已全自动化，**双击 `一键Root.bat` 即可**，平均 10~30 分钟命中，实测单发命中率约 **5~7%**，单 boot 连开 3 发。

**当前状态（交接时）**：提权循环正在后台运行（任务 `WqnWNt`，20 boot × 每 boot 3 发），平板无 root、被反复重启中。

## 3. 漏洞机理与成败本质（技术核心）

### 3.1 完整攻击链（日志验证过）

```
FUTEX_CMP_REQUEUE_PI 死锁回滚（errno=35 EDEADLK）
  → remove_waiter() 用 current 清错任务 → pi_blocked_on 悬空指向已释放内核栈
    → pselect 的 fd_set 栈缓冲放伪造 rt_mutex_waiter（需 res-encode 技巧）
      → sched_setattr 触发 prio chain 遍历 → 撞上伪造 waiter → 写窗口打开
        → rb_erase 更新父节点子指针 = 一次受控 8 字节内核写
          → ★击中目标 = ashmem_miscs->fops（ashmem 驱动 miscdevice +0x10）
            → ashmem fd 的 lseek/pread 走伪造函数表
              → pipe_buffer 建立物理读写（physrw）
                → 遍历 init_task 找到自己（i≈900+）
                  → cred = init_cred，uid 2000→0
                    → sig_enforce 1→0，selinux 1→0
                      → insmod kernelsu.ko → /dev/su → root
                        → 成功后自动扫全进程清"毒页"防 panic
```

### 3.2 成败的本质（重要！别被日志误导）

- **竞态窗口 92% 都开**（`write_window=1`），失败**不是**竞态没踩上
- **`lseek-oracle replaced=0` 是坏探针**——连成功那次也报 0，**不要用它判断成败**
- **真正成败分界 = `pipe physrw` 能否建立**：成功 = `physrw done=1 read_ok=1 write_ok=1`，失败 = `done=0 read_ok=0`
- **失败根因 = 那 8 字节写没落在 `ashmem_miscs->fops` 上**，由内核内存状态随机性决定（页分配器洗牌 / SLUB 空闲链随机 / 页迁移），**用户态无法干预**
- **实证**：开火时 `buddyinfo` 的 order-3 大页仅 1 个（极度碎片化）；root 下清缓存+内存整理后可恢复到 3524 个，且该状态下开火全链 25 秒成功、迁移计数零变化

## 4. 操作方法

### 4.1 标准提权（推荐）

**双击 `一键Root.bat`**（平板插好 USB 即可）。脚本自动完成：重启 → 等 boot → 上滑解锁 → 关 USB 弹框 → 清后台 → 拉 Shizuku → 拉 GhostLock App → 点「一键部署执行」→ miss 则同 boot 再开 2 发 → 全 miss 则重启下一 boot → **命中自动停并打印成功**。

### 4.2 命令行方式（AI/脚本用）

```bash
cd "D:/file/文档/workbuddy/2026-10-13-23-07-58"
export PATH="/usr/bin:/bin:/c/Windows/System32:/c/Windows:$PATH"
MAX_BOOTS=10 SHOTS_PER_BOOT=3 bash .workbuddy/app_root.sh go
```
- **必须用 WorkBuddy Bash 工具的 `run_in_background=true` 启动**（`nohup ... &` 会随调用结束被杀）

- 退出码：0=命中成功；2=跑满未中；3=熔断（连续 2 次 panic）

- **看进度**：`D:\file\文档\workbuddy\2026-10-13-11-14-12\auto_root_logs\` 下最新 `app_root_*.log`（`tail -f` 效果）

## 6. WorkBuddy 环境坑（跨项目通用，务必遵守）

1. **Bash 工具里 `nohup ... &` 的子进程会随调用结束被杀** → 长驻循环必须用 `run_in_background=true` 直接托管
2. **Bash 工具前台 120s 超时**，长任务用后台 + TaskOutput
3. **PowerShell 工具无法弹窗**（Start-Process 被安全策略拦：不得 spawn shell/interpreter）；bash 里调 `powershell.exe` 也被拦
4. **设备死掉时 adb 调用会吃满超时** → 脚本里所有 adb 调用都已加 `timeout`（勿去掉）
5. 系统级工具（schtasks/reg/wmic）被禁；删文件用 .NET API 而非 rm/Remove-Item（本机有 safe-delete guard）
6. 涉及本机默认 120s 超时的命令，长任务一律 `run_in_background`

## 9. 给接手者的最后忠告

1. **默认配方（作者定制 build）就是最优解**——本项目所有"改良"实验全部为负收益，这是花钱花时间换来的结论，别重复踩

3. **保持耐心**：5~7% 单发命中率意味着有时要等 20+ 发，熔断/卡死保护会兜底，设备不会坏
4. **设备是用户的日常主力平板**——跑循环期间会反复重启没法用，用户要用时立刻停循环
5. **判断成败只看 `physrw read_ok`**，别看 `replaced`（坏探针）
