# GhostLock 提权原理分析 —— 从成功/失败日志反推"击中什么才能拿到权限"

> 分析时间：2026-10-14 20:10 ｜ 设备：荣耀 MagicPad 3 (CGL-W00)，内核 `6.1.157-android14-11-g19a495a97bff`
> 数据来源：设备日志（`dc_ksu.log` / `cp.log` / `cfi_state.log` / `cga43499_walk_state` / `ph_all.log`）+ 成功运行留下的 root 权限清理日志 + 公开技术资料（Nebula Security IonStack Part2、CSDN 深度解析、knowlily 荣耀适配笔记）

---

## 一句话结论

**要"击中"的目标只有一个：内核 ashmem 驱动的 `miscdevice` 结构体里的 `fops` 函数表指针（`ashmem_miscs + 0x10`）。**
用 futex PI 竞态构造的"红黑树擦除"原语，把一次 8 字节写打在这个指针上、把它换成伪造的函数表地址，之后对 ashmem 文件描述符的任何操作（lseek/pread）都会跳进攻击者控制的函数 → 任意读写 → 改 cred → 加载 KernelSU。

---

## 一、完整攻击链（内核模块/函数级）

| 阶段 | 内核位置 | 干什么 | 日志证据 |
|---|---|---|---|
| 1. 触发 UAF | `kernel/locking/rtmutex.c` → `remove_waiter()` | `FUTEX_CMP_REQUEUE_PI` 代理锁回滚遇到死锁（-EDEADLK）时，错误地用 `current` 而不是 `waiter->task` 清 `pi_blocked_on` → 真正的等待者醒来后 `pi_blocked_on` 悬空指向**已释放的内核栈** | `CMP_REQUEUE_PI ret=-1 errno=35`（EDEADLK 正是死锁回滚的返回值） |
| 2. 栈复用 | `fs/select.c` → `core_sys_select()` 的内核栈 fd_set 缓冲 | 在悬空指针指向的栈深度上放伪造的 `rt_mutex_waiter`。荣耀 6.1 把 `do_futex` 内联，`PSELECT_WAITER_WORD_SHIFT=11`，必须用 **res-encode** 技巧把值写进"内核写回区"（`res_in/res_out/res_ex`） | `slide res-encode ... want_lock=... ✓` |
| 3. 竞态开窗 | `kernel/futex/*` + `sched_setattr` 优先级调整 | 消费线程抬高等待者优先级 → `rt_mutex_adjust_prio_chain()` 踩上伪造 waiter → 走进 `_raw_spin_trylock(伪造锁)` 失败 → 活锁自旋 = **写窗口打开** | `child_result=1 sched_ok=4 waiter_ok=1 write_window=1` |
| 4. 写原语 | `rt_mutex_dequeue()` → `rb_erase()` | 对伪造 waiter 做红黑树摘除 → **更新父节点的子指针** = 一次受控的 8 字节内核写（目标地址和写入值都由伪造 waiter 的 rb 指针决定） | `write-round #1 enter ... deadlock-accepted / waiter-hold-chain / consumer-firing` |
| 5. **击中目标** | `drivers/staging/android/ashmem.c` 的 `miscdevice`（符号 `ashmem_miscs`，荣耀用复数命名） | 把 `ashmem_miscs->fops`（结构体 +0x10 处的 `file_operations *`）改写成伪造函数表地址 | `WRITE-GEOM target=...f3c340`（= kaslr_base + 0x25F3C340 = ashmem_miscs+0x10）`fake_fops=ffffff88...9000` |
| 6. 验证 | 对新开的 ashmem fd 做 `lseek`/`pread` | 若 fops 被换掉，返回值会变成伪造函数表的返回 → `replaced=1` | `lseek-oracle pre=-1/0 new=-1/0 replaced=0`（失败时） |
| 7. 物理读写 | `fs/pipe.c` 的 `pipe_buffer` | 有了任意函数调用后，用 pipe 的 buffer 建立稳定内核读写 | 成功：`pipe physrw read_ok=1 write_ok=1 rw64=1/1 uid=2000->0`；失败：`done=0 read_ok=0 write_ok=0` |
| 8. 提权 | `init_task` 遍历 + cred 替换 | 遍历 `init_task.tasks` 链表找到自己 → 把 `task->real_cred` / `task->cred` 改成 `init_cred` → 关 `sig_enforce`、SELinux | `uid=2000->0`、`getenforce` 变化 |
| 9. 落地 | KernelSU late-load | `insmod` 免签名 `kernelsu.ko` → `/proc/modules` 出现 `kernelsu ... Live` → `/dev/su` | `kernelsu 192512 2 - Live (OE)` |
| 10. 自清理 | 全进程内存扫描 | 用刚到手的读写遍历**所有进程**找残留"毒页"（伪造 waiter 页）扫掉，防后续 PI 链 panic | `ph_all.log`：`poison_hunt ... all=1`（扫 pid=1 init 开始的全部进程） |

## 二、"成功"与"失败"的分界线（日志特征对照）

| 检查点 | 成功开火 | 失败开火 |
|---|---|---|
| 竞态窗口 `write_window` | **1** | 92% 的情况也是 **1**（93/101）——窗口几乎总能打开 |
| `p0-physical-write` | `ok=1` | 也 `ok=1`（101/101 全"执行"了） |
| **验证探针 `replaced`** | — | **失败时 0，且 101 次尝试中 0 次 =1** |
| `pipe physrw` | `read_ok=1 write_ok=1 rw64=1/1 uid=2000->0` | `done=0 read_ok=0 write_ok=0 uid=4294967295->4294967295` |
| 结局 | kernelsu Live → root | `APP_FOPS_SINGLE_SHOT ... stopping` → `refusing retry on this boot` → `dc12 exit=255` |

**结论：成败的分界线不在竞态（92% 都赢了），而在第 5 步那 8 个字节有没有真的落到 `ashmem_miscs->fops` 上。**

## 三、三个重要发现

### 发现 1：验证探针在这台机器上是坏的
`cp.log` 累计了 101 次写尝试，`replaced=1` 出现 **0 次**——但 exploit 实际成功过 **3 次**（App 自统计 42 尝试/3 成功）。
⇒ **`lseek-oracle` 在这个内核 build 上检测不到成功写入**（很可能它期望的返回值签名与本 build 的 ashmem fops 行为不匹配）。
**含义**：kit 自己的"miss 判定"不可信。`APP_FOPS_SINGLE_SHOT=1` 停止重试的依据就是这个坏探针——**可能存在"写已经落了、但 kit 以为自己没中而放弃"的情况**。

### 发现 2：失败的唯一可疑点是"页准备的物理落点"
竞态赢了、写也执行了、但目标指针没变 → 那次物理写打到了别的物理页。伪造 fops 表所在的喷页（direct map 区，如 `ffffff88178c9000`）和目标 `ashmem_miscs->fops`（内核镜像 .data）都要经过"虚拟地址 → 物理地址"换算，而换算依赖 `kernel_phys_load / kernel_phys_offset` 两个常数——**官方提取器在 iomem 上推导的 offset 与 kit 内置值不一致**（0x816E0000 vs 0x80000000），说明这个常数在这台机器上不是显然的。
⇒ 若常数在某些 boot 上取值漂移（如内存布局变化），就会出现"窗口开了、写偏了"。

### 发现 3：成功日志是会自毁的
`dc_ksu.log` / `cp.log` 每次 boot 被覆盖，**成功那次的详细日志已经没了**。而命中后循环会停住（不再重启），日志恰好保留——所以**下一次命中时立刻拉取全部日志，就是黄金对照样本**。

## 四、可执行的提升方向（按性价比）

1. **【零成本，立即可做】命中瞬间抢日志** —— 命中后循环停住，把 `dc_ksu.log`/`cp.log`/`cfi_state.log`/`walk_state` 全拉下来。有了成功样本，就能和 99 次失败逐行 diff，定位"成功那一次哪一步不一样"。
2. **【低成本】坏探针的副产品**：既然 `replaced` 不可信，真正的成败信号是 `pipe physrw read_ok` —— 可以把监视重心从 dc_ksu.log 的 `verified` 挪到 physrw 上（对脚本无影响，仅分析口径修正）。
3. **【中成本，需多轮 boot】时序旋钮 A/B**：可 env 调的旋钮里，直接影响第 3/4 步的是 `SLIDE_ENTER_DELAY_USEC`、`SLIDE_SPIN_BURST`、`SLIDE_CMP_WAKE`、`EXPLOIT_ATTEMPTS`。每轮换一组值并记录 `write_window`/`physrw read_ok` 结果，积累 20~30 个样本后看相关性。（注意：每次只动一个旋钮，且避开会造成 panic 的非默认路线。）
4. **【不建议】改 `APP_FOPS_SINGLE_SHOT`**：编译期常量，需二进制补丁；且它存在的理由（保护 PI 树）与"验证探针坏了"叠加，盲改风险高。

## 五、风险注记

- 写原语打偏 = 8 字节写到随机内核位置 → 这就是 **panic**（约 10~15% 开火）和 **SLUB 分配器卡死**（整机假死）的来源。二者是同一枚硬币的两面，**提高命中率的同时必然提高崩溃率**。
- 成功后的 `ph_all.log` 自清理扫描（扫毒页）是成功 boot 相对稳定的原因；失败/panic 的 boot 没有这一步。
- 修复版本：6.1 分支 ≥ **6.1.175**（本机 6.1.157，还在窗口内）；升到 MagicOS 11（Android 17/6.6+）即出窗。

### 6.3 最终结论

- **成败分界线 = `pipe physrw` 能否建立**（成功：直接进入 `root direct: walk`；失败：`done=0 read_ok=0` 就放弃）。前面的 write_window、replaced 全都不构成判据。
- **多连发是最大杠杆**：同一 boot 第 2 发复用第 1 发的 KASLR 泄露与页准备，30 秒即中。已把循环改为 `SHOTS_PER_BOOT=3`（kit 作者配方：2-3 发安全，第 4 发退化），单次运行 = 20 boot × 3 发 = 60 次尝试，按 ~5%/发计算单次运行命中概率 ≈95%。
