## 1. 背景速览（与命中率有关的部分）

- 漏洞：`rtmutex.c remove_waiter()` 回滚路径把 `current->pi_blocked_on = NULL` 写成了错误对象（应为 `waiter->task`），由 `rt_mutex_start_proxy_lock()` 返回 `-EDEADLK` 的回滚触发；引入 commit `8161239a8bcc`，修复 commit `3bfdc63936dd`（2026-04-20 进 mainline）。
  来源：https://madpowah.github.io/2026/07/09/cve-2026-43499-ghostlock-ionstack.html
- 触发：3 个 futex 字 + 3 线程做 `FUTEX_CMP_REQUEUE_PI` 构造 PI 环；**UAF 窗口无限（无时间压力）**，单核也可。缓解 `RANDOMIZE_KSTACK_OFFSET` 把"栈复用命中"变成概率猜测。
  来源：https://madpowah.github.io/2026/07/09/cve-2026-43499-ghostlock-ionstack.html 、https://nebusec.ai/research/ionstack-part-2/
- 原始发现：Nebula Security 的 VEGA LLM 管线（IonStack part II），kernelCTF LPE+escape 稳定度 97%，赏金 $92,337。
  来源：https://nebusec.ai/research/ionstack-part-2/
- 影响面：kernel 5.7~7.1，已修于 6.1.175 / 6.6.140 / 6.12.86。**可行性取决于编译器 PGO/LTO 让 `rt_mutex_waiter` 落在 pselect 栈上 `stack_fds` 用户可控 word 0–14 的哪个位置，与内核版本号本身无关**——这是"同版本有的机子能打、有的机子永远 0 命中"的第一性原因。
  来源：https://raw.githubusercontent.com/JoinChang/ghostlock-oneplus/main/README.md

## 2. 问题 (a)：作者/社区怎么解释"命中率低、哪些因素影响命中"

> XDA 帖内原文未获取；以下是公开一手资料中可查到的解释，可信度从高到低排列。

### 2.1 结构性因素（决定"上限是 0 还是 >0"）

1. **waiter 落点由编译器决定**：`do_futex` 是否被内联、PGO/LTO 布局决定 waiter 落在 `stack_fds` 的哪个 word。OnePlus 系 6.1 因 PGO 内联 `do_futex` 一律不可行（waiter word=13+）；部分 vivo 6.1 可行（word=3）。
   来源：https://raw.githubusercontent.com/JoinChang/ghostlock-oneplus/main/README.md
2. **荣耀系的关键坑（Honor 内联 `do_futex` 进 `__arm64_sys_futex`）⇒ `PSELECT_WAITER_WORD_SHIFT=11`**（正常机型 1~2）。后果：waiter word 0–3 落在 pselect 栈的 `ex[1-4]`（可写），**word 4–10 全部落进 `res_*` 段（res_in 15-19 / res_out 20-24 / res_ex 25-29），被内核 readiness 回写静默丢弃（`default: return 0`）**。老打法只能放 2 个字段（lock/task），结果是 `_raw_spin_trylock(0)` 空指针——**表现就是"永远 0 命中"，属"打法问题，不是概率问题"**。
   来源：https://raw.githubusercontent.com/knowlily/cve-2026-43499-honor/main/README.md 、https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md
   **这与你观察到的 5–7% 低命中高度吻合**：如果你的成品包走的是老（非 res-encode）路径，命中的那 5–7% 很可能只是偶尔轮换/时序凑巧把可写 word 压进 `ex` 段的结果。
3. **`RANDOMIZE_KSTACK_OFFSET`**：nebusec 量化——若栈复用每种可能帧都试不中，开启后"success rate will drop to 1/8 or less，最坏情况 <1.5%"；madpowah 版描述为 1/32 猜测（两个 kernelCTF 靶默认关闭它）。
   来源：https://nebusec.ai/research/ionstack-part-3/ 、https://madpowah.github.io/2026/07/09/cve-2026-43499-ghostlock-ionstack.html
   但**对目标内核反而可能有利**：Honor 仓实测 `CONFIG_RANDOMIZE_KSTACK_OFFSET=y` 而 `_DEFAULT` 未设置 ⇒ **默认不启用，shift 确定、单候选 ⇒ 一次 reboot 扫一个候选**。
   来源：https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md

### 2.2 运行时因素（决定"有 >0 时抖动多大"）

4. **CPU 亲和/双核竞争**：利用需要两个核（主线程 hammer `select`/`pselect` + consumer 线程扰动 waiter 优先级）。默认钉大核，可用环境变量 `GHOSTLOCK_CORE` / `GHOSTLOCK_CONSUMER_CORE` 覆盖；**同核会增加争用**（官方 profile `recommended_cpus: main=0, consumer=1`）。真实翻车案例：ghostlock-app issue #382（Honor Magic7 Lite，5.10.252）——**App 默认 CPU 对 4,5，但该机 cpuset 是 0-3,6-7，`sched_setaffinity` 报 EINVAL 数百次 ⇒ KernelSnitch `mm_struct` 泄漏每次失败；改选 6,7 后 EINVAL 消失、泄漏成功**，之后也只有 1/4~1/2 的尝试能走下一步。
   来源：https://mkonic.github.io/redmagic-wiki/rm10pro/ghostlock-temp-root 、https://raw.githubusercontent.com/YuKongA/ghostlock-app/master/docs/kernel_profiles/defaults.md 、https://github.com/YuKongA/ghostlock-app/issues/382
5. **开火时机 / uptime / 旁路干扰（quiet window 的实质）**：Honor 仓复盘一例成功样本——**成功日志从 uptime 171s 开始、包在 107s 启动**；结论是 KernelSnitch 的 `mm_struct` 泄漏与 pipe page 新鲜度**对启动时刻极其敏感，因为"用 adb fork 出来的手动轮询进程会扰动 slab/分配器"**。他们最终配方：`SETTLE_UPTIME=175`（对齐 171s 那个槽位）、`EXPLOIT_ATTEMPTS=16`（包默认 8）。并称"per-hit-time slot constant（命中时刻槽位恒定）"。
   来源：https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md
6. **链路超时（quiet/route window）**：官方 profile 里 `race.route_wait_ms=1000`、`race.route_done_timeout_ms=300000`——**超时即 fail-stop，因为 PI 所有权无法安全回滚**；`routes.select_stack.enter_delay_us=50000`（文档原话："Directly shifts the select-stack race window"，**这是最直接的"命中窗口平移"旋钮**）；`consumer_max_calls=1`（"The stable path is single-shot"，稳定路径是单发）。
   来源：https://raw.githubusercontent.com/YuKongA/ghostlock-app/master/docs/kernel_profiles/defaults.md
7. **死锁/挂死不是命中率问题而是保真度问题**：`rt_mutex_adjust_prio_chain` 唯一回到链顶的路径是 `_raw_spin_trylock` 失败（`*(u32*)lock != 0`），一旦构造出悬垂链就是**指令级 livelock（yield 自旋）**，样本 run35 `calls=1` 必然挂死；作者结论："末跳是移植保真度问题，不是调参问题"，并**排除了 6 组旋钮**（即调参救不了这类失败）。
   来源：https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md
8. **失败的正常形态**：官方教程原话——"If the phone reboots instead, the race lost — that is the normal failure mode, not damage. Boot back up and run it again; several attempts are expected"（重启=竞速输了，是正常失败而非损坏，重开机再打，多次尝试是预期）。
   来源：https://mkonic.github.io/redmagic-wiki/rm10pro/ghostlock-temp-root

**"未查到"项**：XDA 帖作者 zj520 本人关于 MagicPad3 命中率的原话、"quiet window"这一术语的官方定义，均未查到。

### 3.4 真实"调参提高命中率"案例（用户报告）

1. **CPU 对修复**：ghostlock-app issue #382 —— 默认 4,5 落在 cpuset 外 ⇒ EINVAL ⇒ 泄漏全败；**改 6,7 后泄漏成功，后续 1/4–1/2 成功率**。来源：https://github.com/YuKongA/ghostlock-app/issues/382
2. **`SETTLE_UPTIME=175` + `EXPLOIT_ATTEMPTS=16` + 单发锁**：把开火对齐到已知成功槽位（171s），6 轮 0 命中 → 换打法后成功。来源：https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md
3. **`SLIDE_PSELECT_RES_ENCODE=1`**：Honor 6.1.157 从"结构性 0 命中"到"命中率 40–50%"。来源：同上。
4. **`SLIDE_CONSUMER_MAX_CALLS=1`（而非 400 burst）**：400 会挂死；配合 `ROUTE_DELAY=0`、`ARM_HANDSHAKE=1` 才正确。来源：同上（§8.2 注记）。

### 4.2 同族（Honor 6.1.157 / MagicOS 10.0.0.170）已知坑——对 CGL-W00 有直接参考价值

来源（下述 6 条全部）：https://raw.githubusercontent.com/knowlily/cve-2026-43499-honor/main/README.md 与 https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md （研究对象 Magic6 Pro BVL-AN16，**同 MagicOS 10.0.0.170、同 6.1.157-android14-11 基线，仅 -g hash 不同**）

1. **漏洞未修**：该 build 上 `remove_waiter()` 仍是修复前签名；pipe physrw uid 2000→0 已跑通；`/proc/modules` 里 KernelSU LIVE。
2. **`prctl(PR_SET_MM_MAP)` 官方回收路径被封**：Honor 把 `capable(CAP_SYS_RESOURCE)` 检查前移 ⇒ 栈回收不能走 PR_SET_MM_MAP，必须走 pselect 重编码路线。
3. **`P0_KERNEL_PHYS_LOAD=0xa8000000`**（写 `0x80000000` 会落进 `gunyah_hyp_region`；这是 Mediatek/SoC 公式类错误的镜像坑）。
4. **`MM_STRUCT_SZ=0x400`**：必须取 `/proc/slabinfo` 的 kmem_cache object size，**不是 BTF sizeof（0x3c0）**，取错 ⇒ KernelSnitch 泄漏失败。
5. **ashmem 偏移坑**：`ASHMEM_MISC_FOPS_OFF=0x2682cc0` 是 miscdevice 的 **fops 字段**（符号是复数 `ashmem_miscs`），`ASHMEM_FOPS_OFF=0x12f79d0` 才是 fops 体；**若二者相等说明偏移生成器静默 fallback 出错**（自检判据）。其余：`INIT_TASK_OFF=0x22017c0`、`SELINUX_ENFORCING=0x284b038`、`SLIDE_RANDOM_BOOT_ID_DATA=0x263c3e0`。
6. **Honor 平 rt_mutex_waiter 布局**：`tree_entry@0x00, pi_tree_entry@0x18, task@0x30, lock@0x38, wake_state@0x40, prio@0x44, deadline@0x48, ww_ctx@0x50`。
7. 早期"6.1.128 结构性不兼容"结论**已被证伪**，缺的就是 res-encode 技术。

### 4.3 `configfs errno=22` 的公开解释

- **最接近的公开解释**：JoinChang/ghostlock-oneplus issue #31（OPPO Reno10 Pro+，kernel 5.10.236）——"hitting CFI error=22"：**劫持间接函数指针（ashmem fops → configfs read_iter/write_iter）时 kCFI 类型哈希校验失败，返回 `EINVAL(22)`**。即 errno=22 本质是 **CFI 类型不匹配**，不是 configfs 本身没挂。
  来源：https://github.com/JoinChang/ghostlock-oneplus/issues/31
- 另见 IonStack-S22U 仓 issue #3：configfs **符号被修饰**（`configfs_read_file.llvm.NNN`）导致找不到/写错，以及 `rt_mutex_adjust_prio_chain` 内 `_raw_spin_trylock` panic。
  来源：https://github.com/IonStack-S22U 仓 issues（经 GitHub issue 搜索命中）
- CFI 绕过的正确姿势（NebuSec）：ashmem `fops` 与 configfs 的 `read_iter/write_iter` **签名相同才可直接换**；换完用 `/proc/sys/kernel/random/boot_id` 的 sysctl `.data` 改成 `&nfulnl_logger` 再读成 UUID 泄漏 KASLR。
  来源：https://nebusec.ai/research/ionstack-part-3/
- **未查到**：针对 MagicPad3/CGL-W00 专门的 configfs errno=22 用户反馈帖。

## 5. 问题 (d)：单 boot 连开几发 / 是否每发间重启 / uptime 何时开火

公开资料中最接近"官方建议"的三条一手记录：

1. **"每 boot 一发"规则（run_kit_max.sh 实录）**：
   - **本次 boot 还没开过火 ⇒ 不要重启，直接打**；
   - **本次 boot 已经开过火 ⇒ 重启后再打**；
   - 开火后**在 +8 分钟和 +13 分钟各判定一次，期间不要碰手机**；
   - **成功的那一发必须自停**（"stopping early to avoid further PI-tree damage"）——所以"每 boot 一发"严格说只约束**成功那一发**；
   - **leak（泄漏）阶段的重试是安全的**，"重试本来就是设计的一部分"（`attempts=8 base_delay=20000`）。
   来源：https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md
2. **uptime 何时开火**：成功样本 `SETTLE_UPTIME=175`（对齐 171s 槽位）、包在 107s 启动；**开火时刻对 slab/分配器状态极其敏感，期间不要用 adb 手动轮询制造 fork 噪声**。JoinChang 官方版建议 "Run after boot completes and ADB is ready"。
   来源：https://github.com/knowlily/cve-2026-43499-honor/blob/main/docs/progress_20261011.md 、https://raw.githubusercontent.com/JoinChang/ghostlock-oneplus/main/README.md
3. **红魔教程版**：失败（重启）就重开机再打，多次尝试是预期；**root 不持久，真重启即失**；装模块用 root 管理器的 **Soft Restart**（不要用电源键重启，否则丢 root）；**root 掉了但要恢复移动数据时，不重启、直接再跑一次 GhostLock**；运行期间**不要写任何分区**（BL 锁死 ⇒ EDL 砖）；作者 XDA 备注：关闭系统自动更新。
   来源：https://mkonic.github.io/redmagic-wiki/rm10pro/ghostlock-temp-root

**未查到**：zj520 在 XDA 帖中针对"单 boot 连开几发"的原话答复。

## 7. 对目标机（CGL-W00 / 6.1.157-g19a495a97bff）的可执行结论

1. **先验证是不是"打法问题"**：同基线（Honor 6.1.157 / MagicOS 10.0.0.170）已知 `shift=11`，老路径 waiter 落 `res_*` 被丢弃 ⇒ 结构性 0 命中。若你目前是 5–7% 而非 0%，说明部分命中来自可写 `ex` 段——**换用/确认 `SLIDE_PSELECT_RES_ENCODE=1`（res-encode）路线是最大的单点提升**（公开记录 40–50%）。
2. **把开火对齐到固定 uptime 槽位**（参考成功样本 171s/`SETTLE_UPTIME=175`），开火前后**不要用 adb 轮询制造 fork 噪声**。
3. **`EXPLOIT_ATTEMPTS` 从 8 提到 16**（leak 阶段重试安全；成功那发必须自停）。
4. **确认 CPU 亲和落在该机 cpuset 内**（issue #382 的教训：默认对 4,5 若不在 cpuset ⇒ EINVAL ⇒ KernelSnitch 泄漏全败）。旋钮参考 `KSNITCH_CPU` / `GHOSTLOCK_CORE` / `GHOSTLOCK_CONSUMER_CORE` / `recommended_cpus`。
5. **每 boot 一发**：本 boot 未打过→直接打、不重启；打过→重启再来；成功后 +8min/+13min 静置判定。
6. **`configfs errno=22` 优先查 CFI**（kCFI 类型哈希不匹配，fops 换签名必须同型），而非反复挂载 configfs；同时核对 ashmem `MISC_FOPS(0x2682cc0) ≠ FOPS(0x12f79d0)` 的自检。
7. **别升级 MagicOS 11**（官方社区与 issue #83 均反馈升级后失效）；BL 仍无解，root 为临时、重启即失；运行期间不写分区。
