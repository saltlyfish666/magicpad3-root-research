## 1. 已确认的事实（数据支持）

### 1.1 值级黄金 diff（golden_diff.py / decisive_block.py）
- **写目标恒定**：`target = kaslr_base + 0x253c340`，hit 与 miss 完全一致
  → **排除**交接文档 §3.2 的疑点「kernel_phys_offset 0x816E0000 vs 0x80000000
  漂移导致写偏」（miss 样本的目标偏移同样正确）。
- 写几何 `pc = kernel page prepare 的 base + 0x1000`（命中样本 hit2: prep base
  ffffff8892d18000 → pc ffffff8892d19000，逐字对应）。
- p0=0、canon=1、report=1 等字段 hit/miss 无差异 → 与上一任「写入前无指纹」结论一致。
- cp.log 的 geom 块 = 每发的写轮次（~101 块），跨 boot 累积不清空。
- 每个样本文件恰好 2 个块 target 偏移=0x26fca40（=0x253c340+0x1C0700），
  hit/miss 都有 2 个 → 历史 SELINUX_ROUTE 残留，无判别力。

### 1.2 页准备序列 = 成败模式（prep_pattern.py）★核心发现
| 样本 | prepare_kernel_page 序列 | 结果 |
|---|---|---|
| hit (20:44) | fail#1 → **VALID#2** → 立即 physrw | HIT |
| hit2 (21:18) | fail#1 → **VALID#2** → 立即 physrw | HIT |
| miss（logstudy 完整样本） | 8 连 FAIL → exploit 重启(第2次 attempt) → 3 FAIL → VALID@总第11次 | MISS |
| gw_fire（GW_CHAIN 卡死样本） | fail#1 fail#2 → VALID#3 | (卡死) |

- 第 1 次 prepare **永远 FAIL**（疑似固定 warmup），故有效最早 = 第 2 次。
- ~~**2/2 命中都是"第 2 次就找到页"；样本量小，但方向明确：
  找页速度 ≈ 内核内存状态质量，可作逐发内存状态探针（无需 root）。**~~
  ⚠ **已被 Run A 基线推翻简单版（见 §4）**：18 发 miss 的
  prep_fails=[4,0,2,0,0,2,1,6,1,5,5,3,1,0,0,0,5,0]，含大量 fails=0 的 miss
  → 找页快 ≠ 会命中；命中(fails=1,1)与 miss 分布重叠，无判别力。
  探针保留价值：测"内核对页狩猎的响应"，作 GROOM 实验主指标。
- 二进制默认 `EXPLOIT_ATTEMPTS=8`（OPTS 显示 <unset> 时 attempt=x/8，
  页准备 retry x/8 与 exploit attempt x/8 共用同一计数 8）。
- miss 的写发生在"找了 11 次才找到"之后 → 晚找到的写疑似"坏状态下的写"。

### 1.5 环境事实
- `/proc/buddyinfo`、`/proc/pagetypeinfo` **shell 无权限**（Permission denied）；
  vmstat/zoneinfo/meminfo 可读 → 无 root 拿不到碎片化直读，必须靠代理指标。
- 平板 `/tmp` = tmpfs 3.78GB **shell 可写**（/mnt /dev 不可写）→
  **用户态碎片整理可行**：dd 大块到 /tmp → rm → 伙伴合并（纯内存、不碰闪存）。
  机理依据：root 下 compact 后 order-3 1→3524 时全链 25s 成功（n=2，含污染）。
- MemAvailable 当前 ~2.9GB（boot 稳定后）。

## 5. 深夜技术分析结论（01:30-02:00，三路子代理 + 实测）

### 5.1 Run C 结局：GROOM 判定有害并弃用（app_root_1015_004151.log）
- 30 发 0 中、prep_fails mean≈3.9（vs 基线 1.94）、**3 次 240s jam + 1 次内核 panic**
  （01:02 boot_id 05c07a85→ae5e2960，熔断累计 1/阈值 2）→ tmpfs 大规模 dd 对页狩猎
  是减速而非整理，且推高卡死/panic 率。不再重试 GROOM 路线。

### 5.2 黄金法证（forensic_report.md，脚本 forensic_mine/cp_rounds/ph_aff.py）
- **写前无预兆再获确证**：PRE 段 key=value 全量扫描（3 HIT vs 41 MISS + 43 dcshot）
  完全不重叠项 = 0。分岔在 `p0 physical write status=0 ok=1`（双侧相同）**之后**的
  CFI 恢复：HIT `cfi misc_fops readback ret=8 (restored)` → verified=1 step=0；
  MISS `restore via configfs FAILED ret=-1 errno=22` → verified=0 step=6。
- errno=22 的公开最接近解释 = kCFI 类型哈希校验失败 EINVAL（JoinChang#31），
  不是 configfs 缺失。随机性就发生在"写那一下"落没落到 fops。
- walk_state 三份 68B 字节全同；cfi_state.log 四档前缀嵌套 100% 同值 → 无事前指纹。
- 数据缺口（miss 侧无 aff_diag、逐发无 cp.log）已由 v2 新增存档补齐（见 5.4）。

### 5.3 XDA/研究仓调研（XDA_research_report.md）
- **res-encode 不是杠杆：我们的 kit 已默认走该路径**。全部 51 份日志
  `slide res-encode consumer firing` 恒 4 条、`returned flag missing` 恒 0（hit/miss 相同）；
  二进制无 SLIDE_PSELECT_RES_ENCODE 环境键（编译内置）。研究仓"40-50%"是移植修复后
  的路径命中率，与本 kit 实测 4-7% 不是同一口径。
- KSNITCH_CPU=8 是 kit 自己的默认（dc_ksu_run.sh 行52 `export KSNITCH_CPU=8`），
  本机 nproc=8（0-7）且命中样本同为 8、mm drain 正常 reap → 不是 issue#382 越界问题。
- **EXPLOIT_ATTEMPTS 语义实测（Run B）**：控制 exploit 外层重启次数（attempt=1/2、
  attempt=2/2），**不改** prepare_kernel_page retry 的 /8 上限；attempt2 的 delay
  25000→20000。二进制 setenv 会自算 PSELECT_DELAY_USEC/SLIDE_ENTER_DELAY_USEC 默认值。
- 其它线索：tcp_zerocopy attempts=2000 注释"too low reduces hit rate"；select_stack
  enter_delay_us=50000 "directly shifts the race window"；每 boot 规则=打过就重启、
  成功那发自停（v2 已符合）；勿升 MagicOS 11.0.0.109。
